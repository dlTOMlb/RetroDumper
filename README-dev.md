# RetroDumper 開発者向け資料

RFCA の通信プロトコルと、機種ごとの吸い出し方をまとめたものです。  
使い方は [README.md](README.md) にあります。

プロトコルの公式仕様は公開されていません。  
ここに書いてあることは、シリアル通信の解析と、動作実績のある実装の逆コンパイルで確かめたものです。

## ビルドと起動

```bash
dotnet build RetroDumper.sln -c Release
```

```bash
dotnet run --project src/RetroDumper.App -c Release
```

テスト（実機不要。  
カートリッジのバスデコードをシミュレートして検証します）:

```bash
dotnet test
```

### 単体 EXE を作る

.NET ランタイムを同梱した 1 ファイルの exe を `dist/RetroDumper.exe` に出力します。  
.NET のインストールされていない PC でもそのまま動きます（約 60MB）。

```bash
dotnet publish src/RetroDumper.App -c Release -o dist
```

単一ファイル・自己完結の指定は `RetroDumper.App.csproj` に書いてあります。  
以前はこれをコマンド引数で渡していたため、引数を付け忘れた publish が`dist` の単一ファイル EXE を通常構成の 156KB で上書きしてしまいました。  
忘れようのない場所に置いてあるので、上のとおり素直に叩けば済みます。

## RFCA の通信プロトコル

シリアル通信の解析を基に実装しています。  
公式仕様は非公開です。

### 物理層

| 項目 | 値 |
|---|---|
| クラス | USB CDC（仮想 COM ポート） |
| ボーレート | 115200 bps, 8N1 |
| フロー制御 | なし |

### フレーム形式

すべてリトルエンディアン。

```
リクエスト (20 バイト)
  +0  u32  opcode
  +4  u32  0x00000008   (固定)
  +8  u32  size
  +12 u32  address
  +16 u32  size         (再掲)

リード ACK (8 バイト)
  +0  u32  0x00000000
  +4  u32  size

ライト ACK (8 バイト)
  00 00 00 00 00 00 00 00

状態要求 (12 バイト)
  06 00 00 00  00 00 00 00  04 00 00 00

状態応答 (12 バイト)
  byte[8] がカートリッジ種別
```

### ウェイクアップ（必須）

**`0x2F` を送るまで、カートリッジはデータバスを一切駆動しません。**どのアドレスを読んでも `0xFF` しか返らないため、これを忘れると「アダプタは応答するのに ROM が読めない」という状態になります。

```
0x2F 00 00 00 | 08 00 00 00 | 00 00 00 00 | 00 00 00 00 | 01 00 00 00
                              size=0        addr=0        param=1
→ 応答 8 バイトのゼロ
```

データ本体のやり取りは伴いません。  
送信後 0.5 秒ほど待ってから読み出しに入ります。  
本アプリは最初の読み書きの直前に自動で 1 回だけ送るので、利用者が意識する必要はありません。

実機（星のカービィ3 / SA-1）での確認結果:

```
送信前 $00:FFC0 : FF FF FF FF ...            （全バイト 0xFF）
送信後 $00:FFC0 : 48 4F 53 48 49 20 4E 4F ... （"HOSHI NO KIRBY 3"）
送信後 $C0:0000 : 18 FB E2 30 9C 00 42 C2 ... （65816 のリセットコード）
```

解析元では SF メモリカセットのウェイクアップでのみ使われていましたが、通常の ROM 読み出しにも必要でした。

なお、ウェイクアップ直後の 1 回目の読み出しは先頭バイトが化けることがあります（`'H'` が `0x00` になる事例を実機で確認）。  
本アプリは捨て読みを 1 回挟んで回避しています。

### GBA だけフレームが違う

GBA のリードは、他機種と 2 点違います。**どちらも実機で確認済み**です。

> **訂正（2026-09-23）**: ここには以前「GBA はフレーム 2 つ目のフィールドが
> `0x00` でないと拒否される」「転送サイズは 512 固定で 2 / 16 / 1024 は拒否される」
> と書いていました。**どちらも実在しない制約でした。**
>
> `gba-busprobe-20260923-174605.txt` の実測:
>
> | 振った軸 | 範囲 | 結果 |
> |---|---|---|
> | フレーム 2 つ目のフィールド | `0x00`〜`0x0F` | **全 16 通り受理** |
> | 転送サイズ | 1〜2048 | **全 12 通り受理** |
> | アドレス | 0〜0x1000000 | **全 12 通り受理** |
>
> 40 通りすべてが受理され、すべて全バイト `0xFF`、末尾状態応答も完全に同一
> (`000000000400000006000000`)。`0x20` は引数を一切検証していません。
>
> 当時「拒否」と見えていたのは、読み出しの前に自動で `0x2F` が送られて
> 拒否され、その状態で後続のリードが弾かれていたためです。
> 自分のコードが作った症状を実機の制約と誤認し、それを前提に探索していました。

GBA のリード要求はこの形です（どの値でも受理されるため、下記は一例）。

```
GBA リード要求
  20 00 00 00 | 00 00 00 00 | 00 02 00 00 | <addr> | 00 02 00 00
  opcode=0x20                  size=512               size=512
```

**`0x20` はどんな引数でも受理し、常に全バイト `0xFF` を返します。**カートリッジがデータバスを駆動していない状態です。`0x20` の引数をどう変えてもこれは変わりません。

### ウェイクアップの param はスロット選択

`0x2F` の param は「有効化フラグ」ではなく**スロットの指定**です。  
挿さっているカートリッジに対応する param のときだけ受理されます。

スロット比較で確定した挙動:

| 挿入状態 | 種別 | 受理されるリード | `0x2F` param=1 |
|---|---|---|---|
| 空 | `0xFF` | なし（全部拒否） | 拒否 |
| GBA | `0x06` | GBA のみ | 拒否 |
| SFC | `0x01` | SFC のみ | **受理** → 実データが読める |

受理は `0000000000000000`、拒否は `FFFFFFFF00000000` で判別できます。  
読み出しの成否を待つ必要はありません。

> **訂正**: 以前ここには「param ＝ 種別コード。状態要求で得た種別コードを
> そのまま param に使う」と書いていましたが、これは検証していない思い込みでした。
> SFC では種別コードも param も `1` だったため区別がついていなかっただけです。
> GBA は種別コードが `0x06` ですが、param=6 は拒否されます。
> **種別コードと param は別物**です。GBA に `0x2F` は不要で、
> `0x04` / `0x05` で初期化します（→「スロットの初期化」）。

### リードの手順

ACK を受け取ってもデータ本体はすぐに来ません。**状態要求を「催促」として送る** と、データ本体 `size` バイトと、その状態要求への応答 12 バイトが続けて返ります。

```
PC → RFCA : リード要求 (20B)
PC ← RFCA : リード ACK (8B)
PC → RFCA : 状態要求 (12B)          ← これを送らないとデータが来ない
PC ← RFCA : データ本体 (size B)
PC ← RFCA : 状態応答 (12B)
```

実機（レトロフリーク本体）とは異なる挙動ですが、PC 側からはこの手順でしか読めません。

### opcode

opcode はスロットごとに別番号が割り当てられています。**全表は参照実装（.NET アセンブリ）の逆コンパイルで確定**しました。  
値は 参照実装の各コマンドクラスが基底に渡している番号そのものです。

**制御コマンド**（フレーム長が用途ごとに違う点に注意）

| opcode | 用途 | フレーム |
|---|---|---|
| `0x01` | デバイス識別（`0A 00 37 13` ＝ USB の PID `0x1337`） | 12B |
| `0x04` | スロット選択・給電。param はスロット番号（GBA は 0、SFC は 1） | **16B** |
| `0x05` | スロット確定 | **12B** |
| `0x06` | 状態要求 | 12B |
| `0x2F` | SFC のウェイクアップ。param はスロット番号 | 20B |

**リード／ライト**（すべて 20B、フレーム 2 つ目のフィールドは共通で `8`）

| opcode | 用途 || opcode | 用途 |
|---|---|---|---|---|
| `0x07` / `0x08` | SFC リード / ライト || `0x1F` | **GBA ROM リード** |
| `0x09`〜`0x0C` | SFC 拡張リード / ライト || `0x20` / `0x21` | GBA SRAM リード / ライト |
| `0x0D` / `0x0E` | MD リード / ライト || `0x24` / `0x25` | GBA EEPROM リード / ライト |
| `0x0F` / `0x10` | MD FRAM リード / ライト || `0x27` / `0x28` | GBA フラッシュ リード / ライト |
| `0x11`〜`0x15` | FC CPU / PPU リード / ライト || `0x2B` / `0x2C` | マークIII・GG リード / ライト |
| `0x1B`〜`0x1E` | GB リード / ライト || `0x2D` / `0x2E` | PC エンジン リード / ライト |
| `0x31` / `0x32` | MD EEPROM || `0x33` / `0x34` | FC EEPROM |

> **訂正（2026-09-23）**: 以前この表には `0x20` を「GBA ROM リード・実機検証済み」と
> 書いていましたが**誤り**でした。`0x20` は GBA の **SRAM リード**です。
> セーブが空だと全バイト `0xFF` を返し、しかも引数を一切検証しないため、
> 「受理されるのに `0xFF` しか返らない」という症状になっていました。
> ROM リードは `0x1F` です。SFC ライトも `0x0C` ではなく `0x08` でした。
>
> 誤った値を実機での総当たり探索から推測し、「確定」としてこの表と
> テストに固定したことが、GBA 対応が長引いた直接の原因です。

### スロットの初期化

スロットごとに手順が違います。

| スロット | 手順 |
|---|---|
| **GBA** | `0x04(param=0)` → `0x05` → 200ms 待機 |
| **SFC** | `0x2F(param=1)` → 500ms 待機 |

> GBA に `0x2F` は不要です。param を 0〜255、フレーム 2 つ目のフィールドを
> 2 通り、計 512 通り試しましたが**すべて拒否**されました。
> GBA スロットには `0x2F` の概念自体がありません。
>
> SFC の正規手順は `0x04(1)` → `0x2F(1)` → `0x05` ×2 ですが、
> それに合わせたところ**動いていたカービィ3 を認識しなくなりました**。
> 本家は初期化後に 16KB の捨て読みと最大 5 回のリトライを行っており、
> `0x04` / `0x05` だけを真似ても等価になりません。
> 動作実績のある `0x2F` のみに戻してあります。

### カートリッジ種別コード（状態応答 byte[8]）

| 値 | 機種 |
|---|---|
| `0xFF` | 未接続 |
| `0x01` | スーパーファミコン |
| `0x02` | メガドライブ |
| `0x03` | ファミコン |
| `0x04` | **未確認**（GBA ではないことを確認済み） |
| `0x05` | ゲームボーイ |
| `0x06` | **ゲームボーイアドバンス**（実機検証済み） |
| `0x07` | マークIII / ゲームギア |
| `0x08` | PC エンジン Hu カード |

### アドレスの意味

**リクエストの `address` は ROM ファイル上のオフセットではなく、その機種のバス上のアドレス** です。

- SFC … 24bit のカートリッジバスアドレス（`bank << 16 | offset`）。  
  バンク `$C0`〜`$FF` を直接読める
- メガドライブ … 68000 バス上のバイトアドレス（ROM は 0 番地から）
- マークIII / GG … Z80 のアドレス空間
- GBA … カートリッジバス上のアドレス。**起点は 0**（実機検証済み）

GBA について補足します。  
CPU から見ると ROM は `0x08000000` に見えますが、それはメモリマップ上の話で、**カートリッジのコネクタに `0x08000000` という番地は存在しません**。  
既存の吸い出し機が 16bit ワードアドレッシングで 24 本のアドレス線に `0x000000`〜`0xFFFFFF` しか出していないことからも裏付けられます。

## SA-1 への対応

SA-1 カセットは Super MMC が 1MB ブロック 4 本をバンク `$C0`〜`$FF` に貼ります。**電源投入直後のバンクレジスタ既定値は 0,1,2,3** なので、バンク `$C0`〜`$FF` を順に読むだけで先頭 4MB が連続して取れます。  
市販の SA-1 カセットは最大 4MB（スーパーマリオRPG、星のカービィ スーパーデラックス等）なので、**バンクレジスタへの書き込みは一切不要** です。

既存の吸い出し機も SA-1 を HiROM として扱い、バンク 192 (`$C0`) から`numBanks` 本を読む実装になっており、同じ結論です。

実装上の注意点が 2 つあります。

**ヘッダ位置**SA-1 のヘッダは ROM オフセット `0x7FC0` にありますが、バス `$00:7FC0` では読めません。  
Super MMC がバンク `$00` の `$8000`〜`$FFFF` を ROM 先頭 32KB に貼るため、読めるのは **`$00:FFC0`** です。  
素の LoROM は A15 が ROM に配線されていないので`$00:7FC0` でも `$00:FFC0` でも同じものが読め、これが LoROM と SA-1 の判別材料にもなります。

**プライミング**SA-1 は電源投入後にバンク `$C0` 側へのアクセスが一度もないとヘッダが正しく読めません。  
本アプリはヘッダ読み出し前にバンク `$C0` のダミーリードを 1024 バイト行います（既存の吸い出し機と同じ対策）。

4MB を超える SA-1（市販品には存在しない）の場合のみ、MMC バンクレジスタ`$2220`〜`$2223` を書き替えて 2 枚目のウィンドウを読みます。

## マッパー別のアドレス変換

| マッパー | ROM オフセット → バスアドレス | 上限 |
|---|---|---|
| LoROM | バンク `offset >> 15`、`$8000 \| (offset & 0x7FFF)`。`$7E/$7F` は `$FE/$FF` へ逃がす | 4MB |
| HiROM | バンク `$C0 + (offset >> 16)` | 4MB |
| ExHiROM | 前半 4MB はバンク `$C0`〜`$FF`、後半はバンク `$40`〜`$7D` | 7.875MB |
| SA-1 / S-DD1 | MMC ウィンドウ内をバンク `$C0`〜`$FF` | 8MB |

ヘッダのサイズ欄は 2 のべき乗しか表現できないため、6MB のカセットが 8MB と申告することがあります。  
そのまま読むと WRAM のバンクに踏み込むので、上限で頭打ちにしたうえで警告を出します。**実容量が半端なカセットではサイズの手動指定を使ってください。**

### ヘッダが嘘をつくカセット

以下は容量をヘッダ欄ではなく固定値で扱います（実カセットから確定した値）。

| カートリッジ種別 (ヘッダ `0x16`) | 実容量 |
|---|---|
| `0x43` S-DD1 | 32Mbit (4MB) |
| `0x45` S-DD1 + バッテリ | 48Mbit (6MB) |
| `0xF5` SPC7110 | 24Mbit (3MB) |
| `0xF9` SPC7110 + RTC | 40Mbit (5MB) |
| `0xF3` CX4 | 12 / 16Mbit |

メガドライブはヘッダ `0x1A4` の終端アドレスが実容量より小さいカセット（ウルトラコア等）があるため、ミラー検出による実測値と突き合わせ、大きいほうを採用します。

## GBA の容量判定

GBA のヘッダには容量を申告する欄がありません。  
本アプリは**ROM 終端より先が全バイト `0xFF` になる**ことを利用して実測します。

Crash Bandicoot Advance (ACUJ) での実測:

| 範囲 | 内容 |
|---|---|
| 0MB〜8MB | 実データ |
| 8MB〜16MB | 100% `0xFF` |
| 16MB〜32MB | オープンバスの繰り返し |

ミラー（先頭への折り返し）もワードアドレスの残留値も起きませんでした。  
候補サイズ N の先 `[N, 2N)` を 8 点サンプルし、**すべて `0xFF` のときだけ**終端とみなします。  
参照実装も全 0xFF の判定で同じ判定をしています。

確実を期すなら **No-Intro DAT による照合**を使ってください（→「No-Intro DAT」）。  
一致すれば容量も含めて正規ダンプと同一だと言い切れます。

## ファミコンの容量判定

カセットはヘッダを持たず、タイトルもマッパー番号も容量も申告しません。  
マッパーは利用者が選びます。

容量はバンクの折り返しから実測します。  
ROM に載っていないバンク番号は上位アドレス線が繋がっておらず、番号が丸められて先頭のバンクと同じ内容が見えます。  
バンク 0 と一致する最小の 2 の冪が総バンク数です。

実測値はマッパーが取りうる範囲に収めます。  
範囲は既存の吸い出し機がまとめた容量の表に合わせてあります。

| マッパー | PRG | CHR |
|---|---|---|
| 0 NROM | 16〜32 KB | 0〜8 KB |
| 1 MMC1 | 32〜512 KB | 0〜128 KB |
| 2 UxROM | 64〜256 KB | なし（CHR-RAM） |
| 3 CNROM | 16〜32 KB | 0〜2048 KB |
| 4 MMC3 | 32〜512 KB | 0〜256 KB |

タイトルは吸い出したあと No-Intro DAT で特定し、ファイル名の変更を提案します。

## 書き込み保護とバンク切り替え

「カートリッジへの書き込みを禁止」は、**カセットの内容**（セーブデータ・フラッシュ）が書き換わることを防ぐ機能です。  
既定で有効です。

これとは別に、ゲームボーイの MBC やマークIII のマッパーは、バンクを選ぶために制御レジスタへ書き込む必要があります。**これは揮発性のレジスタで、カセットの内容は変わりません。** 電源を切れば消えます。

以前は両者を同じ扱いにしていたため、書き込み保護を有効にしたまま GB を吸い出せませんでした。  
現在は範囲を明示して分離しています。

| | 保護下で通るか |
|---|---|
| GB `$0000`-`$7FFF`（MBC レジスタ） | 通る |
| GB `$A000`-`$BFFF`（外部 RAM＝セーブ） | **通さない** |
| マークIII `$FFFC`-`$FFFF`（マッパー） | 通る |
| **GBA（全アドレス）** | **通さない** |
| SFC（SA-1 / S-DD1 の MMC） | 通さない（既定値で 4MB 読めるため不要） |

**GBA はこの仕組みから完全に除外しています。** GBA の ROM 読み出しに書き込みは一切不要で、例外も設けていません。

つまり **ROM の吸い出しに、この保護を外す必要はありません。**

## セーブデータ

画面に出すのは `SaveSupport.IsVerified` が true の機種だけです。  
現在はゲームボーイ・ゲームボーイカラー・ゲームボーイアドバンスのみ。**実機で確かめたら 1 行足すだけで出ます。**

絞っている理由は「未検証だから念のため」ではありません。**書き込みの安全網が成立するかどうか**です。

セーブの書き込みは、書いたあとに読み戻して 1 バイトずつ照合しています。  
壊したかどうかを知る手立てはこれだけです。  
この照合が信用できない機種では、機能そのものを出せません。

`SaveMemory`（番地の門）はこれとは別の守りで、緩めていません。  
画面に出さない機種でも、セーブ領域の外へは書けません。  
RfcaLab からの実機実験の経路も残してあります。

### SFC のセーブ RAM — バスが浮く（未解決）

スーパーメトロイド（LoROM / SRAM 8KB）で確かめたところ、**セーブ RAM の窓で読みが常に「直前にバスへ流れた最後の 1 バイト」を返します**（2026-09-26 実機）。

| 操作 | `$70:0000` を 8 バイト読んだ結果 |
|---|---|
| 何もしない | `8585858585858585` |
| `DEADBEEF12345678` を `$F0:0000` に書いた後 | `7878787878787878` |
| 8192 バイトの模様を書いた後 | 全域 `0xBB`（模様の最後のバイト） |

SRAM が選択されておらず、浮いたバスの残留を読んでいます。

**この状態では照合が安全網になりません。**一様なデータ（消去直後のセーブ、大半が同じ値のセーブ）を書くと、1 バイトも届いていないのに照合が通ります。  
バラバラな模様を書いたから気付けただけです。

調べたこと:

- **セーブの読み書きそのものは参照実装と完全に同じ**でした。  
  読みバンク `$70`、書きバンク `$F0`、窓の大きさ、書き込みの手順（ヘッダ 20 バイト → ACK 8 バイト → 本体 → ACK 8 バイト）まで一致。
- 送信フレームも一致（`op=0x08 addr=0xF00000 size=8192`）。  
  WARN も出ていません。
- **違うのはスロットの初期化です。**

```
参照実装:  0x04(1) → 0x2F(1) → 0x05 → 0x05
           → $00:C000 を 16384 バイト捨て読み
           → ヘッダ判定に失敗したら最大 5 回やり直す

現在:      0x2F(1) のみ
```

`0x04(1)` がカートリッジ RAM を有効にしているのではないか、が今の見立てです。  
ROM の読み出しは `0x2F` だけでも通るので、そちらでは露見しません。

以前この手順に合わせたところ、星のカービィ3 を認識しなくなりました（2026-09-23 実機）。**そのとき捨て読みとやり直しを省いていた**ことが今回分かりました。  
次に試すなら、5 回のやり直しまで含めて丸ごと再現します。

なお実験中に `0x04` の直後で未処理の受信が 4 バイト残り、`0x05` が拒否され、アダプタが「未接続」を返す状態になりました。`0x04` は 16 バイト、`0x05` は 12 バイトのフレームなので、生の `SendControl` ではなく`SendSlotSelect` / `SendSlotCommit` を使う必要があります。

### セーブ RAM の窓（実装済み・未確認）

実装は残してあります。  
6 経路あり、**LoROM だけが読みと書きで違うバンクを使います。**

| マッパー | 読み | 書き | 窓 | opcode |
|---|---|---|---|---|
| LoROM | `$70` | **`$F0`** | 64KB | 通常 |
| S-DD1 | `$70` | `$70` | 64KB | 通常 |
| HiROM | `$30:6000` | `$30:6000` | 8KB | **拡張** |
| ExHiROM | `$B0:6000` | `$B0:6000` | 8KB | **拡張** |
| SPC7110 | `$30:6000` | `$30:6000` | 8KB | 通常 |
| SA-1 | `$40` | `$40` | 64KB | 通常 |

参照実装はさらに `LoRomLowAreaOnly` / `SuperFx` / `St010` を持っています（前者は分割幅が 32KB という違いだけ）。

### SaveSize と SaveMemorySize

別物です。  
取り違えると、セーブの読み書きが丸ごと使えなくなります。

| | 意味 |
|---|---|
| `SaveSize` | この吸い出しで ROM の後ろに付けるか。既定はオフ |
| `SaveMemorySize` | カートリッジに載っている容量。セーブだけを読み書きする画面が見る |

SFC は両方を `options.IncludeSaveRam` で切っていたため、チェックを入れない限り `SaveMemorySize` が 0 になり、**案内どおり（オフ）に使うと「セーブ RAM がありません」で必ず止まっていました。**メガドライブは `SaveMemorySize` を設定しておらず常に 0 でした。

### GBA フラッシュの ID は取りこぼす

`ReadGbaFlashId` は 2 バイト目が落ち、メーカー番号の繰り返しを返すことがあります。  
取りこぼす比率は石によってまるで違います。

| 石 | 正しい値 | 取りこぼし | 実測 |
|---|---|---|---|
| Sanyo（ポケモン エメラルド） | `0x1362` | `0x6262` | 交互 |
| SST（黄金の太陽 失われし時代） | `0xD4BF` | `0xBFBF` | **5 回中 1 回しか正しく読めない** |

読み直しは 20 回にしてあります。  
5 回だと SST の石を 33% の確率で「対応していないフラッシュです」と断ってしまいます。

## 診断

opcode は全スロット分が確定したため、探索機能は削除しました。  
診断タブに残っているのは、接触不良や読み出し内容を確かめるための測定だけです。  
いずれも判明済みのコマンドしか送りません。

**スロット比較を記録**状態要求と判明済みリードの結果をログ欄に出します。  
カートリッジを差し替えながら繰り返し押して見比べます。

**GBA 先頭 4KB を採取**アドレス 0 から 4KB を読み、任天堂ロゴ（全 GBA ROM 共通の固定バイト列）を探してヘッダ内容を表示します。  
採取した中身を残すかは、そのつど尋ねます。

**SFC 診断ダンプ**状態要求・バンク `$C0` の読み出し・ヘッダ候補の判定を順に記録します。

## No-Intro DAT による照合

吸い出した ROM を No-Intro の正規ダンプと CRC32 / MD5 / SHA-1 で照合します。  
一致すれば、容量も含めて正規ダンプとバイト単位で同一だと言い切れます。

**DAT は exe に埋め込んであります**（gzip、計 2.1MB）。  
何も用意せずに使えます。  
アダプタが扱える機種はすべて収録しています。

| 機種 | 出典 | 件数 |
|---|---|---|
| Game Boy Advance | No-Intro 20260919-175115 | 3,533 |
| Nintendo Entertainment System (**Headerless**) | No-Intro 20260923-001145 | 4,554 |
| Super Nintendo Entertainment System | libretro-database 2026.08.01 | 4,268 |
| Game Boy | libretro-database 2026.08.01 | 2,254 |
| Game Boy Color | libretro-database 2026.08.01 | 2,566 |
| Mega Drive / Genesis | libretro-database 2026.08.01 | 3,365 |
| Master System / Mark III | libretro-database 2026.08.01 | 1,163 |
| Game Gear | libretro-database 2026.08.01 | 915 |
| PC Engine / TurboGrafx-16 | libretro-database 2026.08.01 | 495 |
| PC Engine SuperGrafx | libretro-database 2026.08.01 | 5 |
| スーファミターボ | libretro-database 2026.08.01 | 13 |

合計 23,131 件。

DAT の形式は 2 種類あり、どちらも読めます。  
No-Intro の配布は XML、libretro-database の配布は clrmamepro 形式（括弧の入れ子になった素のテキスト）です。  
どちらも crc / md5 / sha1 を持つので、照合の確かさは変わりません。

更新版や他機種の DAT を使う場合は、exe と同じ場所の `DataBase` フォルダに`*.dat` を置いてください。  
埋め込みと同じ名前ならフォルダ側が優先されます。

入手先: https://datomatic.no-intro.org/

> **NES は Headerless を選ぶこと。**
> 当アプリが付ける iNES ヘッダはミラーリングの向きなどを推測で埋めており、
> カセットからは読めません。Headered の DAT とは PRG/CHR が完全に正しくても
> 一致しません。照合時はヘッダ 16 バイトを外して比較しています。

```
src/RetroDumper.Core/              吸い出しロジック（.NET 9 クラスライブラリ）
  Transport/                       シリアル通信とフレーム組み立て
  Dumping/                         機種共通の型と実装レジストリ
  Database/                        No-Intro DAT の読み込みと照合
  Probe/                           実機診断の記録
  Snes/ Gba/ Gb/ Nes/ Md/ Sms/ Pce/  機種ごとの実装
  Util/                            チャンク読み出しループ、チェックサム
src/RetroDumper.App/               WPF アプリ
tools/RfcaLab/                     実機を直接叩く CLI（下記）
tests/                             シミュレータによる検証
```

吸い出しロジックは `IRfcaLink` に対して書かれているので、実機がなくてもシミュレータを差し替えて検証できます。

### RfcaLab

画面を介さずに実機を叩く CLI です。  
挙動を調べるときは、まずこれを使います。  
GUI を操作してもらうと往復が増えるうえ、1 回ごとにセーブを危険にさらします。

```bash
dotnet run --project tools/RfcaLab -c Release -- <コマンド> [COM3] [引数]
```

**既定は読み出しのみです。**書き込む操作は名前で区別してあります。

| コマンド | すること |
|---|---|
| `survey` | 挿さっているカセットの素性を手早く調べる |
| `gbhead` | GB のヘッダとアドレス線を確かめる（接触不良の切り分け） |
| `savetype` | GBA のセーブ装置を判定する |
| `savetest` | セーブを吸い出し、同じ内容を書き戻して照合する |
| `flashid` | GBA のフラッシュ ID を 5 回読んで並べる |
| `erase` | セーブを全面同じ値で消す（**書き込む**） |
| `sram` | SFC のセーブ RAM の窓を指定の大きさで読み、折り返しを見る |
| `wsram` | SFC のセーブ RAM に模様を書いて読み戻し、元に戻す（**書き込む**） |
| `sramprobe` | SFC のセーブ RAM に **8 バイトだけ**書いて、バンクを変えて比べる（**書き込む**） |
| `sraminit` | 参照実装の初期化を踏んでから同じ実験をする（**書き込む**） |
| `pcedump` | Hu カードを吸い出して No-Intro と照合する |
| `dbinfo` | 埋め込んだ DAT の読み込み結果を見る（実機不要） |

**一様なデータで確かめようとしないこと。**`wsram` が位置で変わる模様を書いているのはそのためです。  
同じ内容を書き戻す `savetest` では、中身が一様なカートリッジで「書けたのか何もしていないのか」が区別できません。`sram` の折り返し検出も、一様なデータでは全周期で「折り返している」と出るだけで役に立ちません（実際にそれで時間を使いました）。

`-- --help` 相当は引数なしで実行すると出ます。
