# RetroDumper

レトロフリーク カートリッジアダプタ (RFCA) を PC に直結して ROM を吸い出す Windows アプリ。

- SFC の **SA-1 / S-DD1 / ExHiROM** に対応
- GBA・GB/GBC・メガドライブ・マークIII/ゲームギアにも対応
- 未知のスロットの通信 opcode を実機から探索する機能を内蔵

## 必要なもの

- レトロフリーク カートリッジアダプタ（本体は不要）
- USB 延長ケーブル（**Type-A オス ⇔ Type-A メス**）
- Windows 10 / 11（ドライバ不要。CDC クラスドライバが自動で当たる）
- .NET 9 デスクトップランタイム

アダプタ背面には USB ポートが 2 つあります。**吸い出し機側（USB ハブでない方）** を PC に挿してください。挿すと仮想 COM ポートが 1 つ増えます。

## ビルドと起動

```bash
dotnet build RetroDumper.sln -c Release
```

```bash
dotnet run --project src/RetroDumper.App -c Release
```

テスト（実機不要。カートリッジのバスデコードをシミュレートして検証します）:

```bash
dotnet test
```

### 単体 EXE を作る

.NET ランタイムを同梱した 1 ファイルの exe を `dist/RetroDumper.exe` に出力します。
.NET のインストールされていない PC でもそのまま動きます（約 60MB）。

```bash
dotnet publish src/RetroDumper.App -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -o dist
```

## 使い方

1. 「COM ポート」で増えたポートを選び **接続**
2. カセットを挿して **種別再取得**（挿入中カセットが表示される）
3. **カセットを識別** → タイトル・マッパー・容量・チェックサムを確認
4. **吸い出し開始** → 保存先を指定

**セーブデータの吸い出しは既定でオフです。** セーブ領域の配置は機種・マッパーごとに
差が大きく、まだ実機で検証できていないため、当面は ROM 本体の吸い出しに絞っています。
「動作」の `セーブ RAM も吸い出す（未検証）` を有効にすると、ROM と同じ場所に
`.srm` として保存されます。

## RFCA の通信プロトコル

`dumpfreak` v1.1（sankichi.backdrop.jp）のシリアルキャプチャ解析を基に実装しています。
公式仕様は非公開です。

### 物理層

| 項目 | 値 |
|---|---|
| クラス | USB CDC（仮想 COM ポート） |
| ボーレート | 115200 bps, 8N1 |
| フロー制御 | なし |

### フレーム形式

すべてリトルエンディアン。

```
リクエスト (20 バイト)
  +0  u32  opcode
  +4  u32  0x00000008   (固定)
  +8  u32  size
  +12 u32  address
  +16 u32  size         (再掲)

リード ACK (8 バイト)
  +0  u32  0x00000000
  +4  u32  size

ライト ACK (8 バイト)
  00 00 00 00 00 00 00 00

状態要求 (12 バイト)
  06 00 00 00  00 00 00 00  04 00 00 00

状態応答 (12 バイト)
  byte[8] がカートリッジ種別
```

### ウェイクアップ（必須）

**`0x2F` を送るまで、カートリッジはデータバスを一切駆動しません。**
どのアドレスを読んでも `0xFF` しか返らないため、これを忘れると
「アダプタは応答するのに ROM が読めない」という状態になります。

```
0x2F 00 00 00 | 08 00 00 00 | 00 00 00 00 | 00 00 00 00 | 01 00 00 00
                              size=0        addr=0        param=1
→ 応答 8 バイトのゼロ
```

データ本体のやり取りは伴いません。送信後 0.5 秒ほど待ってから読み出しに入ります。
本アプリは最初の読み書きの直前に自動で 1 回だけ送るので、利用者が意識する必要はありません。

実機（星のカービィ3 / SA-1）での確認結果:

```
送信前 $00:FFC0 : FF FF FF FF ...            （全バイト 0xFF）
送信後 $00:FFC0 : 48 4F 53 48 49 20 4E 4F ... （"HOSHI NO KIRBY 3"）
送信後 $C0:0000 : 18 FB E2 30 9C 00 42 C2 ... （65816 のリセットコード）
```

dumpfreak では SF メモリカセットの `wakeup_SFM()` でのみ使われていますが、
通常の ROM 読み出しにも必要でした。

なお、ウェイクアップ直後の 1 回目の読み出しは先頭バイトが化けることがあります
（`'H'` が `0x00` になる事例を実機で確認）。本アプリは捨て読みを 1 回挟んで回避しています。

### GBA だけフレームが違う

GBA のリードは、他機種と 2 点違います。**どちらも実機で確認済み**です。

> **訂正（2026-09-23）**: ここには以前「GBA はフレーム 2 つ目のフィールドが
> `0x00` でないと拒否される」「転送サイズは 512 固定で 2 / 16 / 1024 は拒否される」
> と書いていました。**どちらも実在しない制約でした。**
>
> `gba-busprobe-20260923-174605.txt` の実測:
>
> | 振った軸 | 範囲 | 結果 |
> |---|---|---|
> | フレーム 2 つ目のフィールド | `0x00`〜`0x0F` | **全 16 通り受理** |
> | 転送サイズ | 1〜2048 | **全 12 通り受理** |
> | アドレス | 0〜0x1000000 | **全 12 通り受理** |
>
> 40 通りすべてが受理され、すべて全バイト `0xFF`、末尾状態応答も完全に同一
> (`000000000400000006000000`)。`0x20` は引数を一切検証していません。
>
> 当時「拒否」と見えていたのは、読み出しの前に自動で `0x2F` が送られて
> 拒否され、その状態で後続のリードが弾かれていたためです。
> 自分のコードが作った症状を実機の制約と誤認し、それを前提に探索していました。

GBA のリード要求はこの形です（どの値でも受理されるため、下記は一例）。

```
GBA リード要求
  20 00 00 00 | 00 00 00 00 | 00 02 00 00 | <addr> | 00 02 00 00
  opcode=0x20                  size=512               size=512
```

**`0x20` はどんな引数でも受理し、常に全バイト `0xFF` を返します。**
カートリッジがデータバスを駆動していない状態です。
`0x20` の引数をどう変えてもこれは変わりません。

### ウェイクアップの param はスロット選択

`0x2F` の param は「有効化フラグ」ではなく**スロットの指定**です。
挿さっているカートリッジに対応する param のときだけ受理されます。

スロット比較（`slot-comparison.txt`）で確定した挙動:

| 挿入状態 | 種別 | 受理されるリード | `0x2F` param=1 |
|---|---|---|---|
| 空 | `0xFF` | なし（全部拒否） | 拒否 |
| GBA | `0x06` | GBA のみ | 拒否 |
| SFC | `0x01` | SFC のみ | **受理** → 実データが読める |

受理は `0000000000000000`、拒否は `FFFFFFFF00000000` で判別できます。
読み出しの成否を待つ必要はありません。

> **訂正**: 以前ここには「param ＝ 種別コード。状態要求で得た種別コードを
> そのまま param に使う」と書いていましたが、これは検証していない思い込みでした。
> SFC では種別コードも param も `1` だったため区別がついていなかっただけです。
> GBA は種別コードが `0x06` ですが、param=6 は拒否されます。
> **種別コードと param は別物**で、GBA の正しい param は未確定です。
> この誤った等式が、GBA 対応が長く進まなかった直接の原因でした。

### リードの手順

ACK を受け取ってもデータ本体はすぐに来ません。**状態要求を「催促」として送る** と、
データ本体 `size` バイトと、その状態要求への応答 12 バイトが続けて返ります。

```
PC → RFCA : リード要求 (20B)
PC ← RFCA : リード ACK (8B)
PC → RFCA : 状態要求 (12B)          ← これを送らないとデータが来ない
PC ← RFCA : データ本体 (size B)
PC ← RFCA : 状態応答 (12B)
```

実機（レトロフリーク本体）とは異なる挙動ですが、PC 側からはこの手順でしか読めません。

### opcode

opcode はバス（スロット）ごとに別番号が割り当てられています。

| opcode | 用途 | 状態 |
|---|---|---|
| `0x06` | 状態要求 | 確定 |
| `0x2F` | スロットのウェイクアップ | 確定（実機検証済み） |
| `0x07` | SFC リード | 確定 |
| `0x0C` | SFC ライト | 確定 |
| `0x0D` | メガドライブ リード | 確定 |
| `0x2B` | マークIII / GG リード | 確定 |
| `0x2C` | マークIII / GG ライト | 確定 |
| **`0x20`** | **GBA ROM リード** | **確定（実機検証済み）** |
| ? | GBA ライト | **未確定** |
| ? | GB / GBC リード / ライト | **未確定** |
| ? | ファミコン PRG / CHR リード | **未確定** |
| ? | PC エンジン リード | **未確定** |

未確定のものは「opcode 探索」タブから実機で特定します。

### カートリッジ種別コード（状態応答 byte[8]）

| 値 | 機種 |
|---|---|
| `0xFF` | 未接続 |
| `0x01` | スーパーファミコン |
| `0x02` | メガドライブ |
| `0x03` | ファミコン |
| `0x04` | **未確認**（GBA ではないことを確認済み） |
| `0x05` | ゲームボーイ |
| `0x06` | **ゲームボーイアドバンス**（実機検証済み） |
| `0x07` | マークIII / ゲームギア |
| `0x08` | PC エンジン Hu カード |

### アドレスの意味

**リクエストの `address` は ROM ファイル上のオフセットではなく、その機種のバス上のアドレス** です。

- SFC … 24bit のカートリッジバスアドレス（`bank << 16 | offset`）。バンク `$C0`〜`$FF` を直接読める
- メガドライブ … 68000 バス上のバイトアドレス（ROM は 0 番地から）
- マークIII / GG … Z80 のアドレス空間
- GBA … カートリッジバス上のアドレス。**起点は 0**（実機検証済み）

GBA について補足します。CPU から見ると ROM は `0x08000000` に見えますが、それは
メモリマップ上の話で、**カートリッジのコネクタに `0x08000000` という番地は存在しません**。
cartreader の `readWord_GBA()` が `myAddress >> 1`（16bit ワードアドレッシング）で
24 本のアドレス線に `0x000000`〜`0xFFFFFF` しか出していないことからも裏付けられます。

## SA-1 への対応

SA-1 カセットは Super MMC が 1MB ブロック 4 本をバンク `$C0`〜`$FF` に貼ります。
**電源投入直後のバンクレジスタ既定値は 0,1,2,3** なので、バンク `$C0`〜`$FF` を
順に読むだけで先頭 4MB が連続して取れます。市販の SA-1 カセットは最大 4MB
（スーパーマリオRPG、星のカービィ スーパーデラックス等）なので、
**バンクレジスタへの書き込みは一切不要** です。

sanni/cartreader も SA-1 を HiROM として扱い、バンク 192 (`$C0`) から
`numBanks` 本を読む実装になっており、同じ結論です。

実装上の注意点が 2 つあります。

**ヘッダ位置**
SA-1 のヘッダは ROM オフセット `0x7FC0` にありますが、バス `$00:7FC0` では読めません。
Super MMC がバンク `$00` の `$8000`〜`$FFFF` を ROM 先頭 32KB に貼るため、
読めるのは **`$00:FFC0`** です。素の LoROM は A15 が ROM に配線されていないので
`$00:7FC0` でも `$00:FFC0` でも同じものが読め、これが LoROM と SA-1 の判別材料にもなります。

**プライミング**
SA-1 は電源投入後にバンク `$C0` 側へのアクセスが一度もないとヘッダが正しく読めません。
本アプリはヘッダ読み出し前にバンク `$C0` のダミーリードを 1024 バイト行います
（cartreader と同じ対策）。

4MB を超える SA-1（市販品には存在しない）の場合のみ、MMC バンクレジスタ
`$2220`〜`$2223` を書き替えて 2 枚目のウィンドウを読みます。

## マッパー別のアドレス変換

| マッパー | ROM オフセット → バスアドレス | 上限 |
|---|---|---|
| LoROM | バンク `offset >> 15`、`$8000 \| (offset & 0x7FFF)`。`$7E/$7F` は `$FE/$FF` へ逃がす | 4MB |
| HiROM | バンク `$C0 + (offset >> 16)` | 4MB |
| ExHiROM | 前半 4MB はバンク `$C0`〜`$FF`、後半はバンク `$40`〜`$7D` | 7.875MB |
| SA-1 / S-DD1 | MMC ウィンドウ内をバンク `$C0`〜`$FF` | 8MB |

ヘッダのサイズ欄は 2 のべき乗しか表現できないため、6MB のカセットが 8MB と
申告することがあります。そのまま読むと WRAM のバンクに踏み込むので、
上限で頭打ちにしたうえで警告を出します。**実容量が半端なカセットでは
サイズの手動指定を使ってください。**

### ヘッダが嘘をつくカセット

以下は容量をヘッダ欄ではなく固定値で扱います（cartreader が実カセットから確定させた値）。

| カートリッジ種別 (ヘッダ `0x16`) | 実容量 |
|---|---|
| `0x43` S-DD1 | 32Mbit (4MB) |
| `0x45` S-DD1 + バッテリ | 48Mbit (6MB) |
| `0xF5` SPC7110 | 24Mbit (3MB) |
| `0xF9` SPC7110 + RTC | 40Mbit (5MB) |
| `0xF3` CX4 | 12 / 16Mbit |

メガドライブはヘッダ `0x1A4` の終端アドレスが実容量より小さいカセット
（ウルトラコア等）があるため、ミラー検出による実測値と突き合わせ、
大きいほうを採用します。

## opcode 探索

GBA・GB・FC・PCE は opcode が未確定です。「opcode 探索」タブから実機で特定します。

**自動特定（推奨）**
GBA と GB は ROM 先頭に任天堂ロゴという固定バイト列があります。
これが読めた opcode が正解だと断定できるので、ボタン 1 つで確定します。
GBA は ROM 先頭アドレスが `0x08000000` 起点か `0` 起点かも同時に判定します。

**全走査**
アドレス・サイズ・opcode 範囲を指定して総当たりします。応答した opcode が
一覧に出るので、内容を見て採用先を選びます。

> **注意**: 総当たりで当たった opcode がライト系だった場合、アダプタは続けて
> データ本体を待ちます。通信の同期を保つために指定アドレスへ `0xFF` を送り返す
> 必要があり、これが実際のカートリッジへの書き込みになりえます。
> マスク ROM のカセットでは実害はありませんが、**フラッシュ書き換え対応カセットや
> 貴重なカセットでは実行しないでください。**

## 現状の制限

| 項目 | 状態 |
|---|---|
| SFC (LoROM / HiROM / ExHiROM / SA-1 / S-DD1) | 実装済み。SA-1 のヘッダ読み出しとバンク $C0 アクセスは実機確認済み |
| SFC SPC7110 | バンク `$C0`〜`$FF` に見える 4MB のみ |
| メガドライブ | 実装済み。実機未検証 |
| マークIII / ゲームギア | 実装済み。実機未検証 |
| GBA | opcode・フレーム仕様は実機確定。容量判定はミラー検出による推定 |
| GB / GBC | opcode 探索が前提。MBC1/2/3/5 のバンク切り替えを実装 |
| セーブデータ全般 | **既定でオフ**。実装はあるが実機未検証 |
| GBA EEPROM セーブ | 未対応（専用のシリアル手順が必要） |
| ファミコン | 未実装（opcode 未判明。PRG/CHR で別バスのはず） |
| PC エンジン | 未実装（opcode 未判明） |
| SF メモリカセット | 未対応（`dumpfreak` が対応済み） |

**実機検証は部分的です。** 星のカービィ3（SA-1 / 4MB / SRAM 32KB）で、
ウェイクアップ・ヘッダ読み出し・バンク $C0 からの ROM 読み出しが
正しく動くことまで確認しています。吸い出し全体の完走とチェックサム照合は未確認です。

それ以外はカートリッジのバスデコードをシミュレートした 62 件のテストで検証しており、
ROM オフセット ⇔ バスアドレスの変換が往復で一致することを確認しています。

GBA の容量自動判定については、cartreader も自動判定は行わず
手動選択またはデータベース参照にしています。本アプリのミラー検出／オープンバス検出は
補助手段と考えて、既知の容量と食い違う場合は手動指定してください。

## 構成

```
src/RetroDumper.Core/     吸い出しロジック（.NET 9 クラスライブラリ）
  Transport/              シリアル通信とフレーム組み立て
  Dumping/                機種共通の型と実装レジストリ
  Probe/                  opcode 探索
  Snes/ Gba/ Gb/ Md/ Sms/ 機種ごとの実装
  Util/                   チャンク読み出しループ、チェックサム
src/RetroDumper.App/      WPF アプリ
tests/                    シミュレータによる検証
```

吸い出しロジックは `IRfcaLink` に対して書かれているので、実機がなくても
シミュレータを差し替えて検証できます。
